## Why the maintenance path needs to differ

The [October 18 maintenance window](REVIEWED_PAR_WINDOW_20261018.md) closed safely
when reviewed sessions remained. A subsequent owner-authorized read-only
investigation found those original sessions gone and reproduced the problem with
new owned clients: after client close, Supavisor retained the idle backend; another
client reused that same PID. The existing guard can therefore block on operator
pool leftovers. Timing does not prove ownership of the original retained PIDs.

The investigation also verified that this computer could connect directly over
IPv6 to the designated database using certificate/hostname verification and a
read-only login. Closing a direct client removed its backend from observation.
That dated investigation preceded this implementation and is not hosted
acceptance of the new code.

Supabase distinguishes client connections to a pooler from its server-side
database connections ([pooling and limits](https://supabase.com/docs/guides/database/connecting-to-postgres/pooling-and-limits)).
Do not exempt all idle/Supavisor sessions or cache an earlier-owned PID as safe:
pool backends can be assigned to another client. The historical writer guard is
unchanged and still refuses reviewed idle clients, unknown application writes,
hidden activity and incomplete login visibility.

## Explicit separate configuration

Both the export CLI and par adapter add `--maintenance-direct-ipv6`. Without it,
the established session-pooler path remains the default. The par CLI refuses a
direct URL without explicit opt-in. The historical index CLI is unchanged.

The option reads **only `MAINTENANCE_DATABASE_URL`** from the supplied private
owner file. There is no fallback to `DATABASE_URL`, process environment, Render
settings or an app pool. Dotenv interpolation is disabled in this mode, so
environment-variable references cannot supply the URL indirectly. Use a separate current-user/SYSTEM-owned file under
`%LOCALAPPDATA%/JayMaxBuild/credentials`; direct export and the par adapter verify
its ACL. Do not edit the app dotenv file or copy secrets into Git, Pages, shell
arguments or screenshots. No real maintenance config is generated by the tests.

The URL must designate exactly `db.<expected-project>.supabase.co`, port 5432,
database `postgres`, and login `postgres`, with an existing password. Pooler URLs,
other projects/hosts/actors/databases, missing or placeholder passwords, query
overrides, fragments and alternate ports are refused. A separate config is an
operator input, not permission to execute SQL.

## Connection and export checks

`backend/maintenance_connection.py` uses the existing trusted-CA TLS policy and
requires hostname validation plus `CERT_REQUIRED`. Its asyncpg connection class
captures the actual transport peer and TLS evidence. Every returned connection
must use native IPv6 on port 5432; IPv4, mapped IPv4, plaintext or missing evidence
holds. The read-only identity probe verifies database, session/current actor,
positive backend PID, effective label and requested default read-only setting.
Its own transaction is explicitly read-only. Ignored startup settings hold rather
than being silently accepted or overridden.

Connection/identity work has a bounded 20-second budget and 5-second cleanup.
Failure, cancellation or validation refusal closes only the newly owned client;
cleanup failures preserve the original error and safe categories. No SQL backend
signals or selection by role/label are introduced. The existing apply operation
budget, writer checks, locks, exact-plan approval and independent fresh-connection
reconciliation remain unchanged.

For `pg_dump`, an IPv6-only DNS lookup supplies `PGHOSTADDR`, while `PGHOST`
retains the canonical designated hostname for `verify-full`. Inherited PG routing
variables are scrubbed as before; no IPv4 or pooler fallback is attempted. Export
retains its read-only snapshot, authenticated encryption, separate key, bounded
subprocess cleanup and publication-after-close requirements. An exported archive
still requires a matching disposable restore before a hosted plan can qualify.

The par plan already binds the administrative host, port, actor, CA hash and
connection mode. The new module is included in its source hashes. All future
pending reviews, backups and plans must be prepared against the newly accepted
code; old preflight hashes are not reused or repaired.
